# /qa-analyze — QA Impact Agent v1.9

> Скилл + суб-агент для Claude Code. Анализирует задачу перед тестированием: читает Jira и diff MR в GitLab, строит карту влияния, выдаёт фокусированный тест-скоуп — и по запросу генерирует полные тест-кейсы с шагами.

---

## Что делает

Вместо того чтобы тестировщик вручную разбирал Jira-тикет и угадывал что проверять — агент делает это за ~3 минуты, читая **реальный код изменений**, а не только описание задачи.

1. Находит MR в GitLab по ключу Jira-задачи
2. Читает diff рискованных файлов
3. Сравнивает что Jira заявляет vs что реально сделано в MR
4. Строит карту влияния: `[FACT]` / `[HYPOTHESIS]` / `[UNKNOWN]`
5. Находит скрытые зависимости, которые тестировщик, читая только Jira, пропустит
6. Оценивает риск по доменным правилам, а не по размеру диффа
7. Выдаёт фокусированный тест-скоуп: P0 (обязательно) / P1 (рекомендовано) / P2 (опционально) — без фиксированных капов, объём определяется реальным риском диффа
8. По запросу: генерирует полные тест-кейсы с предусловиями, шагами и ожиданиями после каждого шага
9. Постит тест-кейсы в Jira комментарием — форматированный шаблон с `##`-заголовками и нумерованными TC, через `--from-file`

---

## Использование

```
/qa-analyze DEV-2795
/qa-analyze DEV-2795 --mr=frontend-repo/1148   # пропустить Discovery, использовать конкретный MR
```

После анализа агент спрашивает:
> "Расписать полные тест-кейсы с шагами? (P0 / P0+P1 / все)"

---

## Режимы анализа

| Режим | Когда | Что делает |
|---|---|---|
| **Light** | Analytics, текстовые правки, конфиг без логики | Только список файлов, P0 |
| **Standard** | Обычная фича, понятный скоуп | Полный анализ, таргетированный diff для рискованных файлов |
| **Deep** | Auth, платежи, KYC, антифрод, бонусы | Полный diff, расширенный поиск зависимостей |

Deep запускается автоматически, когда заголовок задачи содержит ключевые слова рискованных зон (детерминированный матч по `qa-agent-context.md` → Domain Risk Classification). Подтверждение нужно только если Deep обнаруживается по ходу анализа, а не по заголовку.

## База знаний — как агент узнаёт ваш продукт

Агент читает `config/qa-agent-context.md` перед каждым анализом — домен, зоны риска, накопленные технические правила. Заполняется и пополняется вручную под ваш продукт (см. «Настройка базы знаний» ниже).

Пример правила:
```
[2024-01-15] GGR хранится в центах. GGR_THRESHOLD=35000 = $350 эффективный порог.
             Context: TASK-123
```

> До v1.9 агент сам предлагал 1–3 вопроса после каждого анализа (Seed Mode) — убрано: накопленный бэклог вопросов редко отвечался и не давал сигнала. Правила по-прежнему копятся в `qa-agent-context.md`, просто вручную.

## Установка

### Требования

- [Claude Code](https://claude.ai/code) CLI
- Python 3.9+
- RTK (Rust Token Killer) — компрессор вывода для агента

### Установка RTK

**macOS / Linux:**
```bash
cargo install --git https://github.com/rtk-ai/rtk
```
Или через Homebrew (если доступен).

**Windows:**
```bash
cargo install --git https://github.com/rtk-ai/rtk
```
Нужен [Rust](https://rustup.rs). После установки `rtk` должен быть в PATH.

> RTK необязателен — без него агент работает, но вывод команд может быть длиннее.

### Установка workflow CLI

```bash
git clone https://github.com/hereisnick7/qa-analyze.git
cd qa-analyze
pip install -e .
```

После этого команда `workflow` доступна глобально.

**Windows:** используй `workflow.cmd` вместо `workflow`.

### Настройка credentials

```bash
# Создай папки и скопируй шаблоны
mkdir -p config/jira config/gitlab
cp config/example/jira/.env.example config/jira/.env
cp config/example/gitlab/.env.example config/gitlab/.env
```

#### Jira API token

1. Зайди на https://id.atlassian.com/manage-profile/security/api-tokens
2. Нажми **Create API token**, дай любое название (например `qa-analyze`)
3. Скопируй токен — он показывается один раз

Открой `config/jira/.env` и заполни:
```
JIRA_URL=https://your-org.atlassian.net   # URL вашего Jira (спроси у коллег если не знаешь)
JIRA_EMAIL=you@company.com                # твой email от Atlassian аккаунта
JIRA_TOKEN=сюда-вставить-токен
JIRA_WRITE_ENABLED=true
```

#### GitLab Personal Access Token

1. Зайди в GitLab → правый верхний угол → **Edit profile** → **Access Tokens**
   (или напрямую: `https://gitlab.your-company.com/-/user_settings/personal_access_tokens`)
2. Нажми **Add new token**
3. Название: `qa-analyze`, scope: отметь **read_api**
4. Нажми **Create personal access token**, скопируй токен

Открой `config/gitlab/.env` и заполни:
```
GITLAB_HOST=gitlab.your-company.com   # домен вашего GitLab (без https://)
GITLAB_TOKEN=glpat-сюда-вставить-токен
```

### Настройка базы знаний

Открой `config/qa-agent-context.md` и заполни под свой продукт:
- Название продукта, ключ Jira-проекта, названия GitLab-репозиториев
- Классификацию рисков под свой домен (секция Domain Risk Classification)

**Опционально — флоу продукта:**
Скопируй из своей базы флоу-документации — агент подтянет её автоматически:
```bash
cp ../your-product-docs/product-flows.md config/qa-product-knowledge.md
```

### Запуск

Claude Code нужно открыть **из папки репо** — `.claude/` подхватывается автоматически:

```bash
cd qa-analyze
claude   # или открой папку в IDE с плагином Claude Code
```

Затем в чате:
```
/qa-analyze DEV-2795
```

**Windows:** если команда `workflow` не найдена — используй `workflow.cmd` напрямую,
либо добавь папку репо в PATH.

| v1.2 | Шаг 10: агент предлагает расписать полные тест-кейсы с шагами; постинг в Jira одной командой |
| v1.3 | P0 ordering (реальный user journey первым); форматированный Jira-комментарий (## + нумерованные TC, --from-file); тестовые аккаунты убраны из вывода; база знаний продукта betzo-product/ |
| v1.4 | Startup: Module Index читается первым, агент прыгает только в нужные модули; TC template: поле `Covers:` (ссылка на FACT/HYPOTHESIS из Impact Map); открывающее предложение = конкретное изменение → failure mode; `↳` аннотация только для нетривиальных шагов |
| v1.5 | Жёсткие капы P0/P1/P2 убраны — объём скоупа определяется только риском диффа; каноничный Output Format с машиночитаемым `<!-- qa-meta -->` футером (для `/qa-report` и метрик); Deep-режим по ключевым словам запускается без подтверждения; `--retest` — авто-детект и overwrite+delta вместо append; `jira-comments`/`jira-dev-status` CLI-команды; `/qa-report` шаг 3.5 — метрики читаются из отредактированного QA-комментария в Jira, а не спрашиваются с нуля |
| v1.6 | Шаг 10 переписан — тест-кейсы формулируются как шаги-действия (что реально делает тестировщик: админка/UI/наблюдаемое поведение), а не как цепочка сырых API/DB-вызовов; смысл проверки — в первом предложении TC, до технических деталей |
| v1.7 | Добавлены Responsive/Cross-Device TC для новых UI-элементов на проде; API Testing сужен до чисто контрактных задач без UI-поверхности (если у эндпоинта есть админка/экран — шаг пишется как действие в этом UI); Jira Discovery — полная история комментариев + скачивание текстовых вложений перед анализом |
| v1.8 | Новый Step 8.5 «Чек-лист» — всегда генерируется (в отличие от опциональных тест-кейсов), быстрый список для ручной проверки, дистилляция P0/значимых P1; добавлен в канонический Output Format и в Jira-комментарий (`/qa-analyze` шаг постинга); Step 10 — новый формат `SC-NN` (Test Scenario) для 2+ пунктов, делящих реальное время/среду (общий таймер/стенд), рядом с атомарными `TC-NN`, с сохранением изоляции для дебага per-инстанс; новая техника `Pairwise Coverage` для 3+ независимых многозначных параметров вместо полного кросс-продукта; обязательный финальный consolidation-проход перед выводом (дедуп дублей, свёртка в SC/pairwise) |
| v1.9 | Seed Mode убран — накопленный бэклог вопросов не давал сигнала (редко отвечался, редко нёс реальную информацию); база знаний (`qa-agent-context.md`) теперь пополняется вручную, а не автосбором вопросов.
